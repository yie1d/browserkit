browserkit / architecture tour

一个为 AI Agent 保持浏览器上下文的本地运行时

bk 是短生命周期 CLI，daemon 才是持有 CDP 连接、Session、Target ownership、事件订阅与持久化状态的核心边界。

架构导览 项目定位系统拓扑启动链路 Session 与 Tab请求与能力层并发模型 持久化与清理安全边界源码地图设计评价
01 / Positioning

不是脚本包装，而是持久运行时

browserkit 构建在 cdpkit 0.5.0 之上。它将命令行进程与浏览器生命周期分开：Agent 可以连续运行多个独立的 bk 命令，而后台 daemon 保持同一条 CDP WebSocket、同一个登录态和一致的 Tab 所有权。

CLI 是 client解析参数、发送 JSON、保存本地输出，不拥有浏览器状态。
Daemon 是边界管理连接、Session、Watcher、清理、鉴权与持久化。
cdpkit 是协议层负责 typed CDP、Sender、WebSocket 与事件流。

当前二进制只连接用户已经运行并开启远程调试的 Chrome 或 Edge，不负责启动浏览器。默认 Session 复用用户登录态，命名 Session 使用独立 BrowserContext。

03 / Runtime flows

用同一组泳道理解四条关键路径

    04 / Runtime model

    Session 是唯一隔离和活动边界

    Default session

    使用 Chrome 默认 BrowserContext，继承用户 cookie、localStorage 与登录态；可以 attach 用户现有 Tab。

    Named session

    创建独立 BrowserContext，隔离 cookie、storage 和 Tab；适合多个 Agent 并行工作。

    Ownership来源close / cleanup
    Ownedbk open 创建关闭 Chrome Target
    Attachedbk attach 接管只 detach，不关闭用户 Tab

    Tab 创建使用 reservation：先原子占用容量，再创建 Target；初始化失败就关闭新 Target 并释放名额。一个 Target 最多只能属于一个 Session。

    05 / Routing

    命令契约与页面能力分层

    Handler：面向 Agent 的合同

    • connect/open/attach/tabs/close
    • snapshot/act/navigate/wait
    • network/download/dialog
    • session cookies/storage
    • browser/daemon/debug

    中央路由统一解析 Session、更新活动时间并套生命周期锁。

    Page：可复用浏览器能力

    • navigation 与加载等待
    • interaction 与稳定 backendNodeId ref
    • state、state diff 与 token budget
    • capture、find、wait

    底层命令遵守 cdpkit Sender：浏览器级发给 CDP，页面级发给 attached session。

    06 / Concurrency

    固定锁序，保留跨 Session 并行

    session_bind_lock→lifecycle RwLock→target_registration_lock→DashMap entry

    读锁

    普通 Session 命令与 watcher 事件共享读访问。点击等待新 Tab 时，watcher 仍能注册 Target，不会自锁。

    写锁

    Session close、idle cleanup、browser disconnect 和重新绑定独占生命周期；拿锁后重新读取状态和清理计划。

    任何 DashMap entry guard 都不能跨 .await。Target ownership 的查找、reservation、注册和删除由同一个同步 registration lock 串行化。

    07 / Persistence

    状态可恢复，但不伪装浏览器仍在线

    写入

    • schema v1：Session、Tab、ownership、active target
    • 500ms 防抖，request handler 不同步写盘
    • 临时文件加 rename 原子替换
    • 运行时错误写入 last_error，后续继续重试

    读取与保护

    • 只接受严格的 schema v1
    • 未知字段、其他版本或损坏状态进入 fail-closed
    • 启动先把恢复的 Session 标记 disconnected
    • 用户浏览器需再次 bk connect

    清理入口包括 close、session close、idle timeout、browser disconnect、自然断连和 daemon stop。所有入口都遵守 Owned close / Attached detach，并在部分失败时返回结构化 cleanup_errors。

    08 / Security

    本地高权限自动化，需要明确边界

    Daemon

    • 只监听 IPv4 loopback 随机端口
    • 每次启动生成 daemon.token
    • 请求上限 1 MiB
    • 不应暴露到网络

    URL policy

    • 允许 HTTP(S) 的公网、本机和局域网 host
    • 允许标准本地/UNC file: URL 与 about:blank
    • 拒绝 javascript、data、browser-internal 与未知 scheme
    • Chrome 自身 CORS/file 权限仍然生效
    Windows 边界：token 位于用户目录，但当前没有额外设置细粒度 ACL；能够读取该 token 的同用户进程，本质上就能调用这个高权限本地运行时。

    10 / Assessment

    主架构已经收敛，剩余的是内部历史边缘

    合理之处

    • CLI 与持久运行时分离
    • browserkit 与 cdpkit 边界清晰
    • Session 是唯一隔离模型
    • ownership 保护用户 Tab
    • 生命周期锁兼顾一致性与并发
    • 磁盘和事件流都不阻塞主请求

    当前边界

    • 只连接外部已运行的 Chrome/Edge
    • 不保存或管理浏览器进程信息
    • daemon 重启后必须显式 bk connect
    • Attached 只 detach，Owned 才关闭 target
    • Windows token ACL 可继续加强

    最重要的架构主线已经稳定：daemon 管生命周期，Session 管隔离，ownership 管用户资源安全，cdpkit 管协议，CLI 只负责请求和本地输出。

    内容基于当前仓库实现；命令合同仍以 bk --help、README 和 docs/bk-browser/references/commands.md 为准。
